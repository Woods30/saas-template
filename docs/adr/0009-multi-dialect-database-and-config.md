# ADR-0009: 多方言数据库与配置入库

- **状态**：Accepted（2026-11-18）
- **日期**：2026-11-18

## 背景

v0.11.0 的数据库只有一种形态：D1（Cloudflare 的 SQLite），schema 与迁移 SQL 都写在
仓库里，站点配置（品牌、模块开关、SEO）写在 `src/config/website.ts` 的代码常量里。
两个后果：

1. **换库要改代码**。生产上想用 PostgreSQL（备份、并发写、连接池）只能自己改
   `src/db/index.ts` 与 schema，模板没有给出路径。
2. **改配置要发版**。改品牌名、开一个模块都要改代码 → 提交 → 构建 → 部署。
   对「运营后台」这个卖点来说，这是致命的：运营改个标题要等一次部署。

同时，仓库里入库的迁移 SQL 会与手写 schema 漂移：改了 schema 忘了生成迁移，
线上库结构就落后于代码，而且没有任何检查能发现。

## 决策

### 数据库

1. **provider 由环境变量决定**：`DATABASE_PROVIDER` ∈ `sqlite`（默认）/ `d1` /
   `postgres`。它同时决定「运行时连什么库」与「构建期生成哪份 schema」。
2. **两份手写 schema**：`schema.sqlite.ts` 与 `schema.postgres.ts`。drizzle 的
   `sqlite-core` 与 `pg-core` 表定义不通用，无法用一份源码生成两种方言，因此手写两份，
   并由 `tests/unit/schema-parity.test.ts` 盯着逐表逐列一致。
3. **schema 入口是生成物**：`src/core/db/schema.ts` 由 `pnpm db:setup` 产出，内容是
   一行重导出（`export * from './schema.sqlite'`）。生成物不入库：入库会出现
   「一半 sqlite、一半 pg」的 schema，且切方言时会留下旧内容。
4. **运行期校验方言**：provider 与生成物方言不一致时立即抛错并给出 `pnpm db:setup`
   提示。不一致时 SQL 会静默跑错方言，错误往往出现在很远的调用栈上。
5. **迁移不入库**：`pnpm db:setup` 在该方言还没有迁移时生成首份基线，之后
   `pnpm db:generate` 本地生成 + 手工 apply。两个方言各一个目录，SQL 不可混用。
   库结构的事实源是手写 schema，不是 SQL 文件。
6. **D1 没有交互式事务**：`atomic()` 在 PostgreSQL 上走真事务，在 D1 上不包事务——
   原子性靠单条条件更新（`WHERE balance >= amount` 的 UPDATE）保证。
7. **PostgreSQL 连接按请求作用域建立**：Workers 的 isolate 可能在请求之间被冻结，
   跨请求复用的 TCP 连接会失效。

### 配置

8. **配置进数据库**：`settings` 表存六个分组的 JSON（品牌、SEO、社交链接、支付渠道、
   邮件、模块与能力开关）。分组独立校验：某一组坏了只丢那一组，其余照常用。
9. **品牌与 SEO 是唯一进库的两组**：其余文案仍编译期（Paraglide），后台改不了营销长文。
10. **进程内 30 秒 TTL + 保存即失效**：门禁、SEO、页脚这些地方是**同步**读配置的，
    让它们 await 数据库会把整条渲染链变成异步。代价是「改完最多 30 秒全站生效」，
    后台保存这条路径则是即时的（保存后立刻刷新快照）。
11. **密钥不进货��表**：支付 / 邮件的凭据仍只在 env。数据库只存渠道选择与公开参数。
12. **SSR 与客户端读到同一份**：服务端把生效配置写进 `<head>` 的
    `<script type="application/json">`，客户端在 hydration 前读回装上。两边配置不同
    就会 hydration 错位（SSR 渲染了数据库配置、客户端渲染了出厂配置）。
13. **`websiteConfig` 用 Proxy 暴露**：取值时机统一由「当前生效配置」决定，几十个调用点
    不必逐个改成函数调用。

## 后果

- 换库只改环境变量并重新 `pnpm db:setup`，不改代码。
- 迁移不再是「仓库里的历史」，而是「本地生成的产物」：生产 schema 变更必须本地生成后
  手工 apply，否则线上会静默落后。这条必须写进发布清单。
- 改品牌、开关模块不必发版，但**改了也不等于立刻全站生效**：多 isolate 部署时，
  各 isolate 的缓存最长 30 秒后才会刷新（保存接口所在 isolate 是即时的）。
- 模块开关仍以代码里的出厂值为底（`VITE_MODULES` 白名单仍可用于「一份构建发两处」），
  数据库里的分组覆盖它。彻底只读数据库会打断文档站 / 业务站共用一份构建产物的用法，
  这条与最初计划里的「模块开关只读 DB」有出入，记录在此。
- 手写两份 schema 意味着新增表要改两处；一致性测试覆盖表名与列名，但不覆盖索引与
  约束——那部分靠 code review。

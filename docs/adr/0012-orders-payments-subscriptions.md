# ADR-0012: 订单、付款与订阅三层模型

- **状态**：Accepted（2026-11-19）
- **日期**：2026-11-19

## 背景

本仓的支付侧有三类记录，但层次并不完整：

- `payments`：资金事实，管理台「付款」页与个人中心付款记录都读它；
- `subscriptions`：计费契约，管理台「订阅」页读它；
- `checkout_reservations`：每账号一行、**只覆盖订阅**的结账预留，会过期或被删除；
- `collection_orders`：核销渠道专用的购买意图 + 人工核验状态机。

由此产生三个问题：

1. 管理台没有「每次结账尝试」的历史。一次性购买直接跳转 provider，失败与放弃的结账
   完全不可见；转化漏斗因此只能算「注册 → 付款」，缺中间档。
2. 核销订单是「订单」概念，却因为渠道专用而独立成表；审核队列、漏斗与管理台都要
   单独处理它。
3. ShipAny 用一张 `order` 表承载结账尝试、用 `subscription` 表承载订阅契约，管理台
   「Payments / Subscriptions」两个入口各读一张表。本仓要与之一致，缺的是 `order` 这一层。

## 决策

1. **新增 `orders` 表**：每次创建结账写一行，订阅与一次性都写；续费不写。字段只描述
   结账尝试（订单号、用户、provider、商品 / 付费方式、金额、币种、状态、会话与时间），
   不承载资金事实。
2. **新增 `manual_payment_details` 表**，与 `orders` 1:1。金额尾数、收款账户、付款凭证、
   核验人 / 理由、有效期等核销专有字段放这里；金额唯一与结算临界区两条专用索引也留在这张表。
   现有 `collection_orders` 丢弃，不迁历史（模板仓不承诺跨版本迁移，且 core 分支无生产数据）。
3. **`payments` 保持资金事实**，新增可空 `order_id` 外键。历史行留空；新付款写入时关联
   对应订单。核销付款的 `externalId` 仍是订单 id，但不把它当外键用。
4. **`subscriptions` 保持独立的计费契约**。管理台保留两个入口：付款（读 `payments`）
   与订阅（读 `subscriptions`），核销审核另占一个入口（读 `orders` + `manual_payment_details`）。
5. **漏斗口径**：`users LEFT JOIN orders LEFT JOIN payments`，三档为「注册 → 创建结账 →
   付款」；付款档按 `paid / refunded / partially_refunded` 计，退款仍算「付过款」；续费
   不计入结账尝试。
6. **全量重命名 `collection → manualPayments`**：配置键、消息键、TS 类型与
   `provider='collection'` 的存储值一并迁移为 `manual_payments`。

## 考虑过的替代

- **继续用 `checkout_reservations` 当结账尝试**：它只覆盖订阅、每账号一行、会过期删除，
  拿不到历史，也无法统计一次性购买。
- **单张 `orders` 表 + 核销字段可空**：查询最省事，但通用表被渠道细节污染，核销的两条
  部分唯一索引也难以表达。
- **核销订单保持独立，漏斗用 UNION**：改动最小，但「订单」概念仍分两处，审核队列要同时
  读两张表。
- **不做 `orders`，漏斗只做两档**：无法回答「创建结账后有多少人付款」，运营价值最低。
- **用历史 `payments` 反向补建订单**：会造出合成订单，结账时间与真实意图不符，污染漏斗。

## 后果

- 每次创建结账都必须写订单，并保证订单号或 provider 会话的幂等，避免重试产生重复行。
- 管理台付款页仍只展示资金事实；失败 / 放弃的结账尝试只在漏斗与订单审计里可见。
- 历史在线付款的 `order_id` 为空，历史区间的漏斗缺「创建结账」档；这是已知且可接受的
  数据缺口。
- 核销审核队列改读 `orders` + `manual_payment_details`，旧表删除后不再有双写。
- 退款只改 `payments`，不回写订单状态；订单状态只描述结账尝试，避免两套状态互相漂移。

# ADR-0007: 可选业务模块，不建插件机制

- **状态**：Accepted（2026-11-05）
- **日期**：2026-11-05

## 背景

核销型支付的需求原话是「做成 saas-template 的插件」。核查后本仓**没有应用级插件
架构**：没有插件清单、发现机制、生命周期，也没有「插件可贡献路由 / 数据表 / 导航项 /
环境变量」的注册点。全仓 `plugin` / `插件` 的命中只有三类无关物：构建工具插件、
Better Auth 的官方插件（`admin()` / `apiKey()`）、以及各服务的 provider 注册表。

也就是说「做成插件」这句话落地时必须先回答：**插件机制本身要不要一起建**。

## 决策

1. 核销型支付实现为**与 `payment` 平级的可选业务模块**：独立目录 + `websiteConfig`
   开关 + 模块门禁 + `ServiceStatus`，沿用本仓「每个服务一个目录 + 一个 provider
   注册表」的既有惯例。
2. **不建插件机制**。插件机制是架构级立项——要回答插件能贡献什么、生命周期、依赖与
   版本、隔离与升级、与 `init` 脚本的关系——与本期支付需求无关，却会把工期放大数倍。
3. 若将来确实需要通用插件能力，单独立项；本模块届时按插件规约迁移。

## 后果

- 换收款渠道、换核验方式是「加一条配置或加一个实现」，不是「装一个插件」。
- 使用者需要接线：打开模块开关、配置收款账户、在管理台导航登记核验页——这与本仓
  其他模块的接入方式一致，不是零成本启用。
- 收益是不引入一个尚未被第二个用例验证的抽象层。

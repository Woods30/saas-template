# ADR-0013: 移除实例级能力开关、管理台权限门禁与系统设置分类

- **状态**：Accepted（2026-11-19）
- **日期**：2026-11-19

## 背景

系统设置页有 7 个 tab、每张分组卡片各带一个保存按钮；`features.*` 有 5 个实例级开关，
其中 `enableI18n`、`enableFileUpload`、`enableAIGateway` 没有任何使用方，
`enableApiKeys` 与个人中心 API 密钥入口重复，`enableAdmin` 与 RBAC 权限并存。
`modules.auth` 是认证的总闸，但认证方式本身没有独立开关。

ShipAny 的做法不同：没有实例级能力开关；API 密钥归 user features，管理台靠权限点，
上传 / AI 靠配置是否齐备；认证按邮箱 / Google / GitHub 分别开关；设置页每个 tab 顶部
一个保存按钮，分组可折叠，另有一个「自定义配置」tab 存放任意 key-value。

## 决策

1. **删除 `features.*` 全部 5 个开关**。`enableI18n` / `enableFileUpload` /
   `enableAIGateway` 是死配置；`enableApiKeys` 由用户中心功能开关取代；`enableAdmin`
   由权限点取代。能力是否可用改由依赖配置是否齐备决定。
2. **删除 `modules.auth` 总开关**。认证可用性由「邮箱登录 / Google 登录 / GitHub 登录」
   三个方法开关决定；保存设置时至少保留一个，防止把自己锁在门外。新增 GitHub OAuth。
3. **管理台门禁改为权限点**：`matchPermission('admin.*', permissions)` 为真即可进入。
   `super_admin` 持 `*`、`admin` 持全部 admin 权限、`editor` 持内容 / 工单权限也能进，
   菜单项与接口再按权限点逐项显隐与校验。
4. **新增用户中心功能开关**：账单 / 人工核销 / API 密钥 / 通知偏好，控制个人中心入口
   是否展示；与模块开关分开——模块开关决定能力是否存在，功能开关决定入口是否出现。
5. **系统设置重新分类为 9 个 tab**：基础与外观 / 用户 / 内容模块 / 认证与安全 / 支付 /
   邮件 / 分析 / 通知 / 自定义配置。服务模块开关跟随各自 tab；每个 tab 一个保存按钮，
   分组可折叠。删除空壳与死配置后不保留「全局能力」组。
6. **「用户」tab** 承载用户中心功能开关、注册默认角色（viewer / editor）与注册赠送积分
   （启用 / 数量 / 有效天数 / 描述）。
7. **新增「自定义配置」tab**：`settings` 表中不属于注册表字段的任意 key-value，保留键
   校验、密钥掩码与加密；仅服务端 `getCustomSetting(key)` 可读，不进入公开配置。

## 考虑过的替代

- **保留 `enableAdmin` 作为总闸**：运维上多一道保险，但与 RBAC 重复，且让「有权限」
  和「开关打开」两个条件互相纠缠。
- **保留 `role === 'admin'` 判断**：会漏掉 `super_admin` 与按权限点工作的 `editor`，
  与 RBAC 的设计不一致。
- **按 provider 拆启用开关**（ShipAny 的 stripe_enabled / creem_enabled 等）：本仓的
  provider 是实例级单选，拆成多个开关没有选择意义；保留模块级开关即可。
- **每张卡片各自保存**：粒度更细，但页面按钮过多，且同一 tab 内的字段常需要一起生效。
- **自定义配置全部公开**：实现最省事，但任意键都可能被写进公开配置，泄露风险不可控。

## 后果

- 移除 `modules.auth` 后认证路由始终存在；三个方法全关会被保存校验拦住，但直接改数据库
  仍可造成无法登录，文档需标注这一运维风险。
- `editor` 可以进入管理台，必须确保菜单与每个 server function 都按权限点校验，不能只靠
  入口隐藏。
- 删除的配置键会在 `settings` 表留下孤儿行，需要一次清理迁移。
- 自定义配置绕过注册表的类型校验；保留键、键格式与密钥命名规则由服务层强制。
- 注册赠积分需要幂等键（如 `signup:<userId>`），防止注册重试重复发放。
